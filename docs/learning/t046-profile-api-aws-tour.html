The one-sentence version

A browser sends GET /profile with a JWT; API Gateway checks that JWT against a Cognito User Pool and, if it is valid, hands the request to a Lambda function along with the user's identity; the Lambda reads two rows out of a DynamoDB table and returns JSON.

Everything else — the layer, the IAM roles, the CloudFormation stacks, the S3 deployment bucket — exists to make that sentence true. Nothing in this system is a server you can log into. There is no EC2 instance, no container, nothing running while you sleep. You are billed per request and per millisecond of Lambda execution, and at your traffic level that rounds to zero.

The request, hop by hop

This is the part worth internalising. Each hop below is a place where the request can fail, and each failure looks different — which is why last night's CORS bug was confusing.

01
The browser gets a token src/api/client.js

When you signed in, Cognito handed the app three JWTs: an ID token (who you are), an access token (what you may do), and a refresh token. Our client calls fetchAuthSession() and attaches the ID token as the raw Authorization header — no Bearer prefix. A Cognito User Pool authorizer accepts it either way.

02
API Gateway receives it execute-api endpoint

The request lands on a regional REST API. API Gateway matches the path /profile and the method against its route table. Our route is registered as ANY, meaning one route catches GET, POST, PUT, DELETE — all of them.

03
The authorizer runs COGNITO_USER_POOLS

Before your code sees anything, API Gateway verifies the JWT's signature against the User Pool's public keys, checks it hasn't expired, and checks it was issued for this pool. Fail any of those and the caller gets a flat 401 and your Lambda is never invoked — you are not billed, and nothing appears in your logs. That is the single most valuable property of this design: unauthenticated traffic never reaches your code.

04
Lambda is invoked aws_proxy integration

API Gateway packages the whole HTTP request into a JSON event object and calls the function. Critically, it also injects the validated token claims at event.requestContext.authorizer.claims. Your handler reads claims.sub — the user's permanent unique ID — and never validates a token itself. It trusts the gateway. That trust is only safe because the gateway is the only thing allowed to invoke the function.

05
The function reads DynamoDB via its execution role

The Lambda assumes an IAM role that permits DynamoDB reads and writes on exactly one table. It queries PK = "USER#<sub>" for the PROFILE and TARGETS rows. Note there are no AWS credentials anywhere in the code — the role supplies them at runtime through environment variables the SDK picks up automatically.

06
The response travels back verbatim where CORS bit us

With an aws_proxy integration, API Gateway does not reshape the response. Whatever object your function returns — status code, headers, body — is what the caller receives. That is why the missing Access-Control-Allow-Origin header had to be fixed in the Lambda, not in the gateway config. API Gateway was faithfully passing along a response that had no such header, and the browser threw it away.

The failure mode worth memorising

CORS is enforced by the browser, after the response arrives. The server already ran, already wrote to the database, already returned 200. That is exactly what you saw: the network tab showed success, the page showed an error, and the profile had in fact been saved. A CORS error never means "the request didn't happen" — it means "the request happened and the browser refused to let JavaScript read the result."

The permissions

Two directions of permission — the concept most people miss

IAM answers two different questions and they are easy to confuse. The execution role answers "what may this function reach out and touch?" — DynamoDB, logs. The resource policy (AWS::Lambda::Permission in the template) answers "who is allowed to invoke this function?" — only this specific API Gateway.

Both must exist. Without the role, your code gets AccessDenied from DynamoDB. Without the resource policy, API Gateway gets a 500 trying to call you. You will see both in the console below, on two different tabs of the same page.

Mental model

A User Pool is authentication — proving who you are, and getting a JWT that says so. An Identity Pool is authorization to call AWS itself — swapping that proof for temporary AWS credentials. We use the first and not the second. Keeping these two straight is the thing that makes Cognito stop being confusing.

Why this is its own service

IAM and Cognito look like the same problem solved twice, and the split is deliberate. IAM principals are your principals — staff, roles, services — created by an administrator, global to the account, and every one of them a potential path to your data and your bill. AWS caps them in the low thousands per account precisely because IAM was never meant to hold your customers. Application users are the opposite on every axis: there may be millions, they self-register at 3am with nobody approving them, and they must never be able to call an AWS API at all. Folding the two into one system would mean every signup mutates your account's security posture.

The two also answer different questions. IAM asks "may this principal call this AWS API?" — a question about AWS. Cognito asks "is this person who they claim to be?" — a question about your application's domain. That is why there is no path from a Cognito JWT to an AWS API call unless you deliberately build one. Building one is exactly what an Identity Pool does, and the fact that it is a separate, opt-in component rather than the default is the whole point.

API Gateway — the routes you spent last night creating

Two gotchas here

The OPTIONS method has no authorizer, on purpose. A browser's CORS preflight never carries an Authorization header. Protect OPTIONS and every browser request fails before the real one is even sent.

The console's built-in "Test" button bypasses the authorizer entirely. It invokes the integration directly. A passing console test tells you nothing about whether your auth works — which is why we verified with curl against the real URL instead.

Why this is its own service

Lambda's native interface is an invoke API, not HTTP. AWS kept them apart so that Lambda has exactly one job — run code in response to an event — and HTTP is only one of two hundred-odd event sources it accepts alongside S3 uploads, DynamoDB streams, queues and cron. Baking a web server into Lambda would privilege one trigger over all the others. Meanwhile everything a public front door needs — TLS, custom domains, throttling, API keys, caching, WAF, request validation, authorizers, staged deploys — is a large stateful surface with nothing to do with running your code. Keeping it separate means the same front door can sit in front of a Lambda, a container behind a VPC link, or a direct DynamoDB integration with no compute at all. It is also what makes the 401 possible: an enforcement point outside the house can turn people away before they reach the door. (Lambda Function URLs now exist for people who just want a URL — deliberately stripped of nearly all of this, which is the exception proving the rule.)

Why this is its own service

What AWS is actually selling here is a unit of work with an execution role and a lifecycle, decoupled from whatever triggered it — which is why the same function can serve HTTP today and a queue tomorrow without being rewritten. The deeper reason for the separation is that each layer of this system scales along a different axis: API Gateway scales as a request router, Lambda as concurrent execution environments, DynamoDB as partitions. Fusing any two of them would force one scaling model and one cost curve onto both. That separation is also why Lambda enforces statelessness rather than merely encouraging it — nothing guarantees two requests hit the same environment, and that constraint is precisely what lets AWS scale you from zero to thousands of concurrent runs without asking. It is worth remembering that the DynamoDB client cached on global is an optimisation for the case where an environment happens to be reused, never state you may depend on.

Lambda Layers — the shared code, versioned

Console → Lambda → Layers → nutripilotnutripilotLambdaLib

You should see version 2. Layers are immutable: publishing never edits a version, it creates the next one, and functions point at a specific version number. That is why attaching an updated layer is a deliberate act, and why "the layer is updated but the function still runs the old code" is a classic bug — the function was still pinned to version 1.

At runtime the layer's contents are unzipped into /opt, so /opt/nodejs/node_modules lands on Node's module search path and require('nutripilot-lambda-lib/dynamoClient') just resolves.

DynamoDB — see your own profile row

Console → DynamoDB → Tables → NutriPilotTable-dev → Explore table items

Click Run to scan. You should find two rows with PK = USER#<the sub you copied at stop 2> — one with SK = PROFILE holding your weight, height, age and goal, and one with SK = TARGETS holding the calculated macros. This is the data your smoke test wrote.

Single-table design, in one paragraph

Coming from SQL you would expect a profiles table and a targets table. DynamoDB deliberately does the opposite: put everything in one table, and use a compound key so related items share a partition. Because both rows live under the same PK, one Query retrieves them together — no join, one network call, predictable latency at any scale. The cost is that you must design your keys around the queries you intend to make, up front. You cannot improvise new query patterns later the way you can with SQL.

Something to notice while you're here

The PROFILE row carries a GSI1PK attribute like EMAIL#you@example.com — but the table has no global secondary index defined. The code writes a key for an index that does not exist yet. Harmless (it is just an extra attribute), but it means "look up a user by email" does not work today. Worth knowing; not worth fixing until something needs it.

Why this is its own service

DynamoDB is not "a simpler relational database" — it is a different contract. It guarantees single-digit-millisecond latency at any table size, and the only way to promise that is to forbid the operations whose cost grows with your data: arbitrary joins, ad-hoc filtering, scans as a normal access pattern. There is no query planner to rescue a bad query, because there is no query planner at all — you are it, at design time, when you choose your keys. The second reason it exists separately from RDS is that it fits serverless in a way connection-based databases do not: a relational engine holds a limited pool of stateful connections, which collides badly with Lambda scaling to hundreds of simultaneous environments (RDS Proxy is a whole product built to paper over exactly that). DynamoDB's API is stateless HTTPS requests authorised by IAM — which is also why your function holds no database password to store, leak, or rotate.

CloudWatch Logs — watch the invocation you already made

Console → CloudWatch → Log groups → /aws/lambda/profileFunction-dev

Every Lambda invocation writes here automatically — that is what the logs permission in the execution role buys you. Open the most recent log stream and you will see START, then END, then a REPORT line with duration, billed duration, memory used, and — on cold starts — Init Duration.

Compare a cold start against a warm one. The first invocation after idle pays for spinning up the Node runtime and loading your modules; subsequent ones reuse it. That is also why the DynamoDB client in dynamoClient.js is cached on global — so a warm invocation skips rebuilding it.

Where to look when something breaks

These logs are where a 500 explains itself. A 401, by contrast, will never appear here — the authorizer rejected the request before Lambda was invoked. If you are debugging an auth failure and the logs are empty, that empty log is itself the diagnosis.

Why this is its own service

A system assembled from a dozen independent services has no natural place for its telemetry to land. If each service kept its own logs in its own format, correlating one request across API Gateway, Lambda and DynamoDB would be guesswork. CloudWatch is the deliberate account-wide sink, and it keeps three kinds of data apart on purpose: metrics are pre-aggregated numbers that are cheap to query and alarm on, logs are detailed and expensive, events are structured signals. That split is why you can alarm on an error rate without scanning terabytes of text. Being separate also means telemetry outlives what produced it — delete or roll back the function and the logs remain, because they belong to CloudWatch, not to Lambda. And because it is a separate service, writing to it is a distinct IAM grant: a function whose role lacks the logs permission runs perfectly and is silently undebuggable, which is a more common production incident than it has any right to be.

IAM — read the actual permissions

Lambda → Configuration → Permissions → click the role name link

Reaching IAM through the Lambda page saves you hunting for a generated role name. On the role you will find two policies. Open them with the JSON toggle and read the Resource lines — both are scoped to specific ARNs, not "*". The DynamoDB policy names this one table; the logs policy names this one log group.

Also read the Trust relationships tab: it says lambda.amazonaws.com may assume this role. A role is not attached to anything by default — the trust policy defines who is allowed to become it.

Least privilege, made concrete

If this function were compromised tomorrow, the blast radius is: read and write one DynamoDB table, write some logs. It cannot read your Cognito users, cannot touch S3, cannot spin up EC2. That containment is not automatic — it is the direct result of those scoped Resource ARNs.

Why this is its own service

IAM is the single authorisation plane for every API call made anywhere in AWS — every request to every service is authenticated and authorised before that service sees it. That only works if there is exactly one such system; had each service invented its own permission model, there would be no way to audit who can reach what, and no single lever to revoke it. It is global rather than regional for the same reason: a role must mean the same thing everywhere. Two design choices follow and are worth internalising. First, deny by default — nothing is permitted until explicitly allowed, which is why a freshly created Lambda can do nothing at all and every capability in this project had to be granted on purpose. Second, roles rather than users: a role is an identity with no permanent credentials, assumed temporarily, which is why there is not a single access key anywhere in this codebase and nothing needs rotating. Set this beside the Cognito note at stop 2 — IAM guards AWS's control plane, Cognito guards your application's front door, and keeping them apart is what stops a compromised app user from becoming a compromised account.

The road not taken: proxy vs. non-proxy integration

Hop 06 explained that aws_proxy makes API Gateway a dumb pipe, and that this is why CORS had to be fixed in the Lambda. That was a choice, and it had a real alternative. It is worth understanding what the other branch looked like, because the same fork appears in almost every API you will build on AWS.

What the other branch looks like

A non-proxy integration (AWS calls it a custom integration) inverts who owns the HTTP envelope. Instead of handing your function the raw request and returning whatever it produces, API Gateway sits in the middle and translates in both directions. You write a mapping template that turns the incoming HTTP request into exactly the JSON your function wants, and another that turns the function's return value into an HTTP response. You then declare, in the API definition itself, which status codes exist and which headers each one carries.

Under that model last night's bug is structurally impossible. CORS headers become part of the declared response, applied uniformly to every route, and a new handler cannot forget them because handlers do not own headers at all. This is also why the console's "Enable CORS" button is such a trap on a proxy API: it dutifully writes method-response headers that a proxy integration then ignores completely. The button appears to work. The headers are inert.

The trade

DimensionProxy (what we chose)Non-proxy
Who owns the response Your code. Every header and status code is application logic. API Gateway. The envelope is declared configuration.
CORS Must be emitted per-handler. Enforced only by discipline and tests. Declared once, applied everywhere. Cannot be forgotten.
Cost of a change Ship Lambda code. One deploy path. Edit templates and redeploy the API. Two deploy paths.
The mapping language None needed. VTL — untestable locally, undebuggable, failures surface as opaque 500s. Widely considered the worst part of API Gateway.
One function, many verbs Natural. ANY plus an internal dispatcher, which is our design. Awkward. Wants per-method templates, defeating the point of ANY.
Portability of the handler Event shape mirrors a normal HTTP request; moves to Express with little work. Handler is coupled to your specific mapping templates.

One thing that is not a differentiator, despite often being cited as one: request validation against a JSON schema works with either integration type. If you want API Gateway to reject a malformed body before paying for a Lambda invocation, you can have that on a proxy API too.

Why proxy was still right here

Two reasons, one structural and one about scale. Structurally, our whole design is one function behind an ANY method dispatching on httpMethod — non-proxy would have pushed us back toward per-method mapping templates, dissolving the pattern. And in terms of scale, VTL is a real tax paid on every change, justified when an API is large, long-lived, and maintained by a team that includes people who do not write the handlers. This API has two verbs and one author.

So the honest accounting is: we bought a much simpler, more portable, faster-to-change backend, and the price was exactly one thing — response concerns like CORS moved from configuration into application code, where nothing structural prevents forgetting them. That price came due last night.

What replaces the guardrail you gave up

When you move a concern out of configuration and into code, the discipline has to move with it. That is why the fix was not only the withCorsHeaders helper but a test asserting the header on every dispatch path, including the 405. A missing CORS header is invisible server-side — the request returns 200 and only the browser objects — so it is precisely the class of bug that needs a test rather than a code review.

There is a third option you did not have

API Gateway sells two products. This is a REST API (v1). The newer HTTP API (v2) is cheaper, faster, and — the relevant part — lets you declare CORS at the API level in a way that does apply to proxy integrations, with API Gateway injecting the headers on the way out. That is genuinely the best of both branches for a case like ours. It was not available to you because Amplify Gen 1's REST API category generates v1 only. Worth knowing for the next project that starts outside Amplify; the tradeoff is that HTTP APIs drop some v1 features, including request validators, usage plans and caching.

Two safe experiments

Invoke the Lambda directly with a test event

On the Lambda page, Test tab, create an event with this body. It simulates what API Gateway sends after a successful auth — including the injected claims. Use a made-up sub and it will return an empty profile, touching no real data. Keep it to GET: a POST test event would genuinely write to DynamoDB.

The point of the exercise: notice that the claims block is just data in a JSON object. Your function trusts it completely. In production, only API Gateway can put a value there — which is precisely why the resource policy restricting who may invoke the function is a security control, not bookkeeping.

Doing both back to back is the clearest possible demonstration of where the auth boundary sits.

What transfers to any AWS project

Strip away the NutriPilot names and this is a pattern you will meet constantly. Five ideas here are worth more than the specifics:

  • Managed auth at the edge. Validating JWTs is easy to get subtly wrong. Pushing it into API Gateway means unauthenticated traffic never reaches — or bills — your code.
  • Proxy integrations make the gateway a dumb pipe. Convenient, but it means every response detail, CORS headers included, is your application's responsibility.
  • Two directions of IAM. Execution role for what your code may reach; resource policy for who may invoke your code. Different questions, different places in the console.
  • Infrastructure as code is the real deliverable. The console is for looking and diagnosing. Change things in the templates, or your environments drift apart and nothing is reproducible.
  • Design DynamoDB keys around your queries. Not around your entities. This is the hardest habit to build coming from SQL, and the one that determines whether the table scales.
Where to go next, if you want to keep learning

The natural next stop is CloudWatch Metrics for the Lambda — invocations, duration, errors, throttles — and then AWS X-Ray, which traces a single request across API Gateway, Lambda and DynamoDB and shows you where the milliseconds went. Neither is wired up here, and neither needs to be yet.
